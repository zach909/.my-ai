# Ideas

Running list of requested changes to NeuroClaw, with status. Newest requests at the bottom.

Status: ✅ done · 🔨 in progress · ⏳ to do

## Done

- ✅ **One memory model (OneBrain).** The 14 separate `self_ext_N` models are merged into `models && skills/onebrain/`, and every new self-extension is folded into it automatically.
- ✅ **OneBrain on the mesh.** OneBrain's neurons are grafted into the live network as one "OneBrain" region, and its weights are real mesh connections.
- ✅ **Zip Loop send neuron (input and output).** One neuron for 1, one for 0, and one for *send*. Send alternates between off and fully on, and a bit only counts when send fires. That way "0", "00" and "000" are different messages: `0 → send → 0 → send`.
  - Input: each bit is one tick with only the data neuron driven, then one tick with data + send.
  - Output: a bit is read only when the send-out neuron turns on. If it stops firing, the message is over.
- ✅ **Replace the MoE with the net-skill system.** The Mixture-of-Experts router is deleted. Each skill/plugin is a region of the one mesh, and `NetSkillRouter` switches on the regions whose meaning matches the input. Hyperdimensional thinking, all-to-all connections, the Zip Loop and quantum interference are unchanged.
- ✅ **Prompt skills go into the Zip Loop.** Chat hands the prompting skills that apply to a message (up to 3) to generation, and each one is streamed through the neural Zip Loop with the prompt, as `prompting-skills/<name>/SKILL.txt`.
- ✅ **Extension Builder builds directly into the network.** Every edit in the builder (debounced) is synced into the skill's region of the live mesh: new neurons are grafted, edited ones re-placed, deleted ones detached, and connections rewritten. There's a toggle on the builder page. Grafted skills are also registered for net-skill routing, so they actually get switched on.
- ✅ **The AI has access to mods.** The terminal plugin has `list_mods`, `read_mod`, `apply_mod` and `revert_mod` tools. Looking is ordinary file reading. Applying or reverting needs the new `mods.apply` capability (level `system`, under the Workspace switch), which is **not granted by default**: turn it on in Access. The tools check it themselves, so a chat request can't skip it. Applying keeps a backup, and `revert_mod` restores it.
- ✅ **Yes/no questions with a probability.** `YesNoDoorway` (`models && skills/core/yes-no.ts`) and `/api/yes-no/teach` and `/api/yes-no/ask`: teach it examples, then give it a whole email plus "Is this spam?" and it answers yes or no with a calibrated probability. Each question is its own 3-neuron region of the mesh. See `wiki/Yes-No-Questions.md`.
- ✅ **Tools fire from their own neurons.** Every terminal and desktop tool has its own neuron in the mesh (`tool-neurons.ts`). That layer already existed, but its firings were only acted on from the manual Zip Loop endpoint. Now every chat turn calls the tools whose neurons fired: access-checked, with arguments from the Zip Loop's output, and results fed back into the mesh. The calls are listed in the turn's details (`toolCalls`).
- ✅ **Delete the tokenizer.** `tokenizer.js` is gone, and text is its UTF-8 bytes everywhere, the same as the Zip Loop:
  - the chat embedding, OneBrain's neuron labels (`memory_input_b<byte>`), recall, the RLM action space, and the trainer's alphabet;
  - OneBrain models saved with old tokenizer ids are converted to bytes when loaded. The bundled OneBrain was converted, which dropped 3 neurons and 71 connections that sat on the old start/end/unknown markers.
- ✅ **Android app (and iPhone).** See `mobile/README.md`.
  - **Android** (`mobile/android`, native Kotlin; the APK builds): a floating bubble over other apps (tap to talk, drag to move) and a full-screen chat. It talks to NeuroClaw on your PC over your Wi-Fi, and a photo is captured only when you tap **Photo**, sent to the PC as training data (`~/.neuroclaw/captures/`).
  - **Offline:** OneBrain on the phone answers from memory, and messages and photos are queued and sent when the PC is back.
  - **iPhone** (`mobile/ios`, SwiftUI): the same minus the bubble, which iOS does not allow. It needs a Mac to build, and it has not been compiled yet.
- ✅ **Full network on the phone, cross-platform.** The PC's own engine is bundled into one ~100 KB file (`npm run build:phone-brain`) that Android and iPhone both run in a hidden web view. It includes:
  - the mesh with the full equation and OneBrain grafted in (86 neurons);
  - the Zip Loop with send neurons, net-skill routing, and yes/no.

  Without the PC, the phone's own network answers; what it learns is saved between launches. One message takes about 4 to 5 s on a desktop CPU, more on a phone.
- ✅ **Offline on the phone, syncs with the PC.** The phone's own network always answers, even with no connection. Sync (automatic, plus **Sync now**) works both ways, over `POST /api/phone-sync`:
  - phone → PC: conversations (into the PC's learning log), photos, and yes/no examples;
  - PC → phone: the PC's newer OneBrain and its yes/no knowledge.
- ✅ **Zip Loop toggle neuron.** An optional neuron pair (`toggleIn` / `toggleOut`) that flips level on every bit, so the network can tell `0` from `00` even if it holds send on between bits. It restarts low each message. It is live: chat, `/api/zip-loop/run`, the prompt feed, continuous learning and the phone brain all use neurons 6 (in) and 7 (out) through `zipLoopIdsFor()`, falling back to the plain six on a mesh too small to hold them.
- ✅ **Ramp neuron replaces send in the live mesh: one tick per bit.** The live Zip Loop (chat, `/api/zip-loop/run`, prompt feed, continuous learning, phone brain) no longer uses a send neuron. Neurons 4 and 5 are now a ramp in and out that alternate max, min, max, ... from a resting min, and every flip is a committed bit, so input and output are one tick per bit instead of two. A ramp that stops flipping ends the message. The send + toggle protocol is still in `ZipLoopInterface` for callers that pass those ids, but the live mesh doesn't use it. The network will need to relearn how to hear and speak.
- ✅ **No waiting out the quiet ticks.** A send-clocked doorway (`ZipLoopInterface`) ends a run on the first byte the network doesn't send once it has spoken, instead of waiting `quietTicks` (32) more reads.
- ✅ **Every permission, voice-to-text, screen capture (Android).** A **Grant all permissions** button requests every dangerous permission a sideloaded app can actually be granted (mic, camera, contacts, calendar, call log, phone, SMS, location, sensors, Bluetooth, nearby Wi-Fi, media) in one batch. A 🎙 button does live voice-to-text. A **Screen** button takes a one-shot screenshot (fresh `MediaProjection` consent each time — Android allows nothing less) and uploads it as training data, same as **Photo**. System/signature-only permissions (`REBOOT`, `INSTALL_PACKAGES`, ...) are left out: a normal app can declare them, but Android never actually grants them.
- ✅ **Every permission, voice-to-text (iPhone).** A **Permissions** screen (Settings → PC → Permissions) with **Grant all permissions** plus each one individually: Location, Contacts, Calendars, Reminders, Photos, Microphone, Camera, Speech Recognition, Health & Fitness/Motion, Media & Apple Music, Notifications (incl. Critical Alerts), App Tracking Transparency, Bluetooth, HealthKit, HomeKit, Siri & Search, and Face ID/Touch ID. A 🎙 button in chat does live on-device voice-to-text (`VoiceRecognizer.swift`). `UIBackgroundModes: [fetch]` + a real `AppDelegate` background-fetch handler runs a sync whenever iOS wakes the app for one.
  - Three categories have no request dialog at all — an iOS limitation, not a gap here: **Background App Refresh** and **Cellular Data** are set by the person in Settings only (the app can read, not ask); **Files and Folders** is a Mac-Catalyst-only key (plain iOS apps use the system document picker instead).
  - **HealthKit** and **HomeKit** need their capability turned on in Xcode (`NeuroClaw.entitlements` lists both); **HomeKit also needs a paid Apple Developer account**. Until then those two report that plainly instead of a grant. Full Siri Shortcuts (not just authorization) needs a separate Intents Extension target, out of scope here.
  - Not compiled (no Mac available in this session) — same caveat as the rest of `mobile/ios`.
- ✅ **Short-term context: freeze when a turn stops, thaw when the conversation comes back.** `models && skills/core/thread-context.ts`. When an exchange ends (the assistant's message is saved) or a Zip Loop run stops (pass `threadId` to `/api/zip-loop/run`), the mesh's *activity* is frozen for that conversation: neuron states, energies, each neuron's wave and the shared wave pool. Opening the conversation again soon after (15 minutes, `NEUROCLAW_THREAD_CONTEXT_TTL_MS`) puts the neurons back exactly. Only the activity is kept, never the learned network, so what the mesh learned in between is not undone (the one mesh is shared by every chat). Held in memory only: short-term fades, and the replay below is what survives a restart. Tests: `thread-context.test.ts` (real engine, including that a resumed conversation behaves exactly like one never interrupted) and `thread-context-system.test.ts` (the real `continueThread` / `freezeThread` on the live-sized mesh).
- ✅ **Chat history remembered as the same neurons firing (opt-in memory).** The replay (`context-replay.ts`: a few bytes that move the neurons the way the whole history did, "6 times 4 instead of twenty big decimals") was already built and wired into `continueThread`, but on the real mesh it carried nothing: the state after a 58-byte history matched the state after only its last byte to eight decimals, so a 1-byte replay scored 1.000 for any history. Cause: every neuron is recomputed each tick and forgets within about 6 ticks. Fix: the mesh can now keep a memory (`new ZipLoopInterface(engine, ids, { memory: { vale } })`, or `NEUROCLAW_ZIP_MEMORY=0.97` for the whole process; off by default). Non-doorway neurons hold `vale` of their old state each tick (the elastic gate used as inertia), so earlier input stays as a decaying trace. With it, replays are found and match their own history best (4 of 5). **Honest limit:** the memory is the recent stretch only (the last few bytes at 0.97, a few dozen at 0.99), so a replay stands in for the recent part of a chat, not the whole of it. `compressContext` reports `reason: "blind"` and stores nothing when the mesh keeps no trace, instead of a false match.
- ✅ **The Zip Loop can be taught to answer.** `models && skills/core/zip-speech.ts` (`ZipSpeaker`). Nothing in the repo trained the output side, so the loop could only hear. With the memory on, the question leaves a trace in the mesh and a small learned readout (ridge regression solved in closed form, no outside code) turns it into the answer's bits. 8 of 8 taught answers spoken exactly on a sparse mesh and on the live-sized one; with memory off 1 of 4. It is a lookup keyed by the mesh's memory of the question: about 16 questions (6 of 64 at 64), only the tail of a question is remembered, and `recall()` stays silent on questions it does not know instead of guessing. Reading never changes the mesh.
- ✅ **The elastic block now learns as a function of its input, and can protect an old task.** `ElasticCoreBlock` recomputed its driven neuron away on the first tick, so two different inputs gave the identical output. Fixed (driven neurons are held while it settles). `outputSensitivity()` and `applyGradients({ protect })` hold the parameters an old task relies on: learning a second task with no protection destroys the first (error 1.6), with it the first survives (0.02 to 0.45) while the second is still learned; scrambled importance or a plain slowdown protect nothing. The slow experiment is `gate-forgetting.test.ts` (`NEUROCLAW_SLOW=1`).
- ✅ **Routing learns from outcomes, and gibberish is not routed.** Net-skill routing embeds text at 1024 dimensions (88% on queries sharing words with a skill, was 50%), learns from judged outcomes, and no longer routes text that is about nothing (the mesh then runs ungated). Paraphrases with no shared words are still at chance without experience: the router matches character patterns, not meaning.
- ✅ **Visuals: the AI is the back end, the panel is the front end.** `interface/visuals.ts`, on the chat page at `/`. A reply (or anything you type) with a fenced `visual` block is drawn as a live panel. Doing anything to a panel prompts the AI by itself: a click on a control or a changed field is reported with no code from the panel's author, a `data-ai="..."` attribute on an element is a built-in prompt sent along with it, and `ai.send(name, data)` reports anything else. Each report becomes a `[visual event]` turn and the answer can carry the next panel. The **Visual** button opens a workbench (starters, live preview, send to chat), and the "Ask the AI to answer with visuals" switch there adds a one-sentence "be the back end" prompting skill to each turn. Panels run in a sandboxed iframe with no network, storage, popups or page access. See `wiki/Visuals.md`. **Honest limit:** the replies come from the mesh, which has not been taught to write panels, so today the panels you see are the ones you write; the framing and the event loop are in place for when it can.
- ✅ **AI OS mode: convert the computer you have into one where the AI is always there.** `interface/platform/ai-os.ts`, `scripts/ai-os.mjs`, **Settings > AI OS**, `GET`/`POST /api/ai-os`. The computer starts the engine at every sign-in (a systemd user service or autostart entry on Linux, a LaunchAgent on macOS, a hidden per-user startup script on Windows), so a window is just a view onto an engine that is already running. Per-user, no administrator rights, one switch to undo, and it grants the agent nothing: computer access and tool safety work as before. Only the admin at the computer itself can change it. Turning it on never starts a second engine on the port. **Honest limits:** the Linux unit is checked with `systemd-analyze`, the macOS plist with `xmllint`, and enable/disable run end to end against a throwaway home, but nothing here has been run in a real graphical login session, on a Mac or on a Windows PC, so background service stays *limited* in the capability table. No tray icon, hotkey or shell replacement. See `wiki/AI-OS-Mode.md`.
- ✅ **NeuroClaw as the system assistant, where the system allows it.** **Android:** a real default digital assistant (`AssistantService.kt`, `AssistActivity.kt`, `voice_interaction_service.xml`): pick it once under Digital assistant app, then the power-button long press and the home gesture open a chat sheet. **Windows:** a Start menu entry with the hotkey Ctrl+Alt+N. **Debian/Linux:** an application-menu entry and, on GNOME, the shortcut Ctrl+Alt+N added without disturbing existing shortcuts. **ChromeOS:** Alt+Shift+Y in the extension. **Cannot be done, and not attempted:** replacing Siri (macOS has no API for it) or Copilot (a keyboard hook would be the only route, which this project will not build), and a "Hey ..." wake word on Android. **Honest status:** the Kotlin could not be compiled here (no Android SDK; the CI Android job is the first compile), the GNOME logic ran only against a fake `gsettings`, and nothing ran on Windows, a Mac, a phone or a Chromebook. See `wiki/AI-OS-Mode.md`.
